# TerraFend

A mobile-first PWA for Sri Lanka that shows natural hazards and road blockages (floods, landslides, fallen trees, road closures, wild elephants, etc.) on a map, and checks a travel route for hazards along it. Everything must be free to build and host.

It is a portfolio project by a beginner software engineering student.

## Direction

TerraFend is a live hazard map for Sri Lanka, not a turn-by-turn navigation app. It tracks threats on the map, checks a route for them, and (later) offers a reroute when the route is affected. Google Maps handles navigation. Current work: putting all threat types on the map.

## Stack

- React + Vite + TypeScript
- Tailwind CSS
- Leaflet with react-leaflet, OpenStreetMap tiles
- TanStack Query
- vite-plugin-pwa
- i18next + react-i18next (English, Sinhala, Tamil)
- Later: Supabase (PostgreSQL + PostGIS, anonymous auth, storage, realtime, Edge Functions)
- Later: OpenRouteService for routing, called through an Edge Function
- Later data sources: Sri Lanka Irrigation Department river gauges (ArcGIS), Open-Meteo, GDACS, NBRO and Met Department warnings
- Hosting: Vercel

Only the packages needed for the current step are installed. Add the rest when their step starts.

## Supabase

- Project region: Mumbai.
- Data API is on, but "automatically expose new tables" is off. Every new table needs explicit GRANTs for `anon` / `authenticated`, plus RLS policies.
- Automatic RLS is on for new tables.
- Users sign in anonymously, so they use the `authenticated` role.
- The frontend only ever uses the project URL and the anon (publishable) key, read from `.env`.
- Never use the secret or `service_role` key in frontend code. It bypasses RLS.
- Insert a point as the text `SRID=4326;POINT(lng lat)`, longitude first.
- Schema changes live in `supabase/migrations/` as numbered SQL files, run by hand in the SQL Editor.

- Rain across the island combines three sources. Cards say which one a square came from, and carry its credit.
  - Forecast rules (`forecastHour` in `rainForecast.ts`, used by the island map, the route rain and so the chip). Global models flag thunder over the tropics far more often than it happens, and get the place and timing of storms wrong, so the request also asks for `precipitation_probability` (the same single request), and a forecast hour is only a warning when the model is also fairly sure. Thresholds are the named constants `FORECAST_MIN_PROBABILITY` (60%) and `THUNDER_MIN_MM` (7.5 mm/h). Thunderstorm warning: weather code 95-99 and at least 7.5 mm in the hour and at least 60% chance. Heavy or very heavy rain warning: at least 7.5 / 15 mm and at least 60% chance. A thunder-code hour that fails becomes the quiet note "Thunderstorms possible", and a heavy-amount hour that fails becomes "Heavy showers possible" (`PossibleLevel`, kept apart from `MildLevel` so it can never be drawn; a cell keeps it in its own `possible` field, so it doesn't hide a light or moderate hour). These are not drawn on the map at all, because dozens of them made the whole island look stormy. Instead there is one line under Rain in the Layers panel whenever any cell has one ("Thunderstorms possible in parts of the island over the next 3 hours (forecast, low confidence)", or "Heavy showers", or both), and one quiet line in the route panel when the route crosses any (shown whatever the Rain switch says). They are never counted in the chip, the header pill or the route warnings. Everything else uses light and moderate by amount, which keep their squares. A missing chance never counts as a high one. Wording: forecasts say "likely" or "possible", never "expected", and only measured rain (gauges, satellite) is described as having fallen. Forecast cards show the chance ("70% chance of rain"; route stretch cards say "At least 65% chance"). Measured and satellite rules are unchanged (`rainLevel(mm, null)`). The Layers legend text reads the thresholds from the constants. Measured on the real data on 4 Nov 2026 at 11:45 am: 59 thunderstorm cells before the rules, 7 after (52 became "possible"), and no heavy-rain cells either way.
  - Forecast (Open-Meteo, no key): `rainMap.ts` builds a grid of land points (a simplified coastline is embedded to skip sea points, geoBoundaries CC BY 4.0). Spacing starts at 15 km and widens until there are at most 150 points, which comes out at about 22 km and 137 points. One multi-location request (`fetchHourly` in `openMeteo.ts`, shared with the route rain) gets hourly precipitation and weather code in Asia/Colombo time, and each point shows the worst of the next 3 hours with the same rules as the route rain. `useRainMap.ts` caches for 30 minutes, refreshes every 30 and retries once. `fetchRainMap` returns every cell, dry ones too.
  - Satellite (JAXA GSMaP, via waterlevels.lk `/api/rain-map`, `rainMeasured.ts`): a 0.1 degree grid (25 x 42 cells, row 0 is the north, `SATELLITE_GRID` in the code). Each hour is a text of comma-separated values in tenths of a millimetre (checked against the gauges: raw 24 h sums are about 10x the gauge totals). A blank cell means nothing reported. The map uses the last 3 hours the satellite has, taking each cell's worst hour. The newest hour is usually 1 to 3 hours old when it arrives (the site says "1 to 2 hours late", and the file itself was once about 2 hours stale), so a card only says "in the past 3 hours" while the window ended within 90 minutes, otherwise it gives the clock times. Satellite data older than 6 hours is dropped. If the grid description in the answer ever differs from `SATELLITE_GRID`, the satellite part is left out.
  - Gauges (same endpoint): each gauge has measured mm1h, mm3h, mm24h and a reading time. Its rate is the worse of mm1h and mm3h / 3, so a gauge that has just gone quiet after heavy rain still counts. `lastHour` says whether the last hour on its own reached the level. The card and lists say "in the last hour (measured)" when it did and "in the past 3 hours (measured)" when the level only comes from the 3-hour average (`gaugeWhen`). A null number is unknown, never 0, and readings older than 6 hours are ignored. Heavy and above always get a small rain badge beside the gauge (`MeasuredRainMarkers.tsx`); light and moderate need the Rain switch. The card shows "Measured: 25 mm in the last hour · 27.9 mm in 3 hours · 29.4 mm in 24 hours" and the reading time.
  - One grid: `rainSquares.ts` makes one 0.1 degree square per satellite cell that touches land: its middle or any of its four corners passes the coastline check used for the forecast grid. Coastal squares (Colombo, Negombo, Galle) keep their rain, and squares fully at sea are left out. A square whose only land is a tiny sliver away from its middle and corners (a few small islands) is still dropped. Each square is the worse of the satellite value and the forecast value of the forecast cell it falls in (a tie goes to the satellite), and keeps which source decided it, for the card. If one source fails, the other carries on alone, and the Layers panel shows "Measured rain unavailable right now" or "Rain forecast unavailable right now". `RainMapOverlay.tsx` draws all the squares of one kind of rain (heavy, very heavy, thunder, moderate, light) as a single Leaflet polygon, so there are no overlaps, seams or darker strips, plus a polyline of only the outside edges (an edge shared with another square in the same pane is not drawn, so borders never double up). Warnings get a rounded edge in their own colour, light and moderate a thin darker edge. A tap is matched to its square by grid position and opens one card at the tap. Two panes (z-index 380 for light and moderate, 390 for warnings, under the route line and all markers), each faded to 0.5 as a whole. Cards are pinned to the normal popup pane so they stay solid. Cell cards use the normal auto-pan padding but not the zoom-in fit that marker cards have. Hidden while picking a spot.

- Global alerts from GDACS (the UN and EU's Global Disaster Alert and Coordination System; free, no key) are done (`gdacs.ts`, `useGdacs.ts`, `GdacsMarkers.tsx`, `gdacsRoute.ts`). What the API gives: `/gdacsapi/api/events/geteventlist/SEARCH` is a GeoJSON FeatureCollection of Point features (the event's centre). Each has `eventtype` (TC cyclone, EQ earthquake, FL flood, VO volcano, DR drought, WF wildfire), `eventid`, `name`, `alertlevel` (the event's peak: Green, Orange or Red), `episodealertlevel` (its level now, which the app uses), `iscurrent` ("true" or "false" as text), `fromdate`, `todate`, `datemodified` (UTC, without a Z), `affectedcountries`, `severitydata` (magnitude in M, wind in km/h, area in km2 or ha) and `url.report` and `url.geometry`. It allows browser requests (`Access-Control-Allow-Origin: *`), so there is no proxy. It pages 100 events at a time and the plain list carries a whole year of Orange and Red events (83, only 1 current), so the app asks for the last 5 days only (every current event ended within about 4 days), and only keeps events with `iscurrent`. Core request (always): Orange and Red from the last 5 days, plus `country=Sri Lanka` at any level. Green request (only while the Global alerts switch is on, because there are hundreds of Green earthquakes and wildfires worldwide): Green events from the last 5 days, a few pages. Both refresh every 15 minutes (TanStack Query, retry once). A failed load shows "Global alerts unavailable right now" in the Layers panel and nothing else breaks. Relevance: the event lists Sri Lanka as affected, or its location is within 500 km of the island (`GDACS_RADIUS_KM`). For a cyclone, `url.geometry` gives the track pieces (`forecast` false for past, true for forecast) and the forecast area (the `Poly_Cones` shape). Those are fetched for current cyclones whose centre is within 3,000 km, drawn on the map (past track solid, forecast track dotted, forecast area tinted), and the cyclone's forecast track and forecast area count for relevance. Its past track does not: MURASU-26 in November 2026 passed 380 km from the island, then moved up the Indian coast and was 650 km away, and counting its past track would have shown a Red alert for a storm already gone. Orange and Red always show on the map (a diamond with the type's icon, coloured by GDACS level) and count in the threats chip ("2 global alerts"); Green shows only with the switch. The card has the name, type, level, magnitude, wind speed or area, affected countries, the time in Sri Lanka time, a GDACS link, "Not an official warning. Follow DMC for official alerts." and "Data: GDACS (European Commission JRC and UN OCHA)". - Reroute around blocked roads is done (`reroute.ts`, `RerouteSection.tsx`, state in `RoutePlanner.tsx`, the reroute itself held in `HazardMap.tsx` as `alternative`). Only reports with severity blocked within the 150 m buffer trigger it; large-vehicles-only reports, rivers, rain and global alerts stay warnings only. Right under the route summary the panel asks "This route passes N blocked road(s). Find another route?". The `routing` function's route action takes an optional `avoid` list (at most 20 lat/lng points, checked like start and end) and turns each into a square about 200 m across, sent to ORS as `options.avoid_polygons` (a MultiPolygon). ORS's limits on avoid areas are about 200 km² and 20 km across each, with no long thin shapes, so twenty 200 m squares are far inside them. The avoid point is the spot on the route where it passes the report (from `distance_along_m`), not the pin itself, since a pin up to 150 m off the road could make the square miss the road. When ORS finds no route with avoid areas, the function answers "No other route avoids these blocked roads. Take care, or check Google Maps." (`NO_REROUTE` in `routing.ts`) and the original is kept. On the map the original is grey and dashed and the reroute is the normal blue, in its own pane (z-index 455, above the route's rain colours, which fade while a reroute is on offer). The panel shows "New route: 138 km · about 3 h 4 min (+30 km, +40 min) · avoids 1 blocked road", then "Use this route" (it becomes the main route, so hazards, rivers, rain and global alerts are all re-checked) and "Keep original" (the prompt isn't shown again for that route). The reroute's own hazards are checked too: if it passes a different blocked road the panel says so and allows one more reroute that avoids all of them (two reroutes at most per Check route; a reroute that's been used can also be rerouted once more if it still passes a blocked road). Google Maps waypoints: up to 3 points placed on the stretches where the used route leaves the first checked route (more than 300 m from it, at least 500 m long, a long detour gets extra points), stored as `via` on the route and added to the Google Maps link. Check route and Clear route start the reroute over, and a reroute still in progress is dropped. The out-of-date rules apply (buttons disabled while out of date), it hides while picking a spot, and the reroute's reports show on the map too. ## Rules

- Never put API keys in code. Use `.env`, which is git-ignored. Keep a `.env.example` with variable names only.
- Keep the UI mobile-first. Design for a phone screen first, then widen.
- Explain changes simply, because the user is learning.
- Use the Edit tool for file edits, not PowerShell string replacement (it corrupted index.html once).
- Write code comments the way an experienced human developer would: short, plain and natural. Only comment where it helps, explain why something is done rather than restating what the code obviously does, and don't comment every line. No emojis, no decorative section banners, no overly formal or robotic phrasing, and no comments like "This function handles..." on self-explanatory code.
- Don't call the real routing function or OpenRouteService in automated or headless tests; use `?fakeRouting=1`.
- New logic should come with tests. Keep the logic in pure functions (in `src/lib`) where possible, so it can be tested without a browser or network, and add or update its `*.test.ts` file in the same change.
- When testing, never leave a dev server running after you finish, and only stop processes you started yourself.
- All new user-facing text must be added to all three translation files (en, si, ta).
